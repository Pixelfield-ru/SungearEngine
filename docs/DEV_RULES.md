## 📜 Общие правила

### Принципы разработки

| Принцип | Описание | Применение |
|---------|----------|------------|
| **DRY** | Don't Repeat Yourself | Избегай дублирования кода |
| **KISS** | Keep It Simple, Stupid | Простые решения лучше сложных |
| **YAGNI** | You Ain't Gonna Need It | Не добавляй функционал «на будущее» |
| **Data-oriented** | ECS-мышление | Данные в компонентах, логика в системах; не тащить ООП-иерархии туда, где хватает компонента |
| **Convention over Configuration** | Следование конвенциям | [CodingConvention.md](../CodingConvention.md) обязателен для всех проектов Pixelfield |

### 🔄 Инициатива по улучшению документации

**Важное правило**: если ИИ в процессе работы считает, что для качества
выполнения задачи необходимо:
- Изменить существующие документы (USER_RULES, DEV_RULES, PROJECT_STRUCTURE, SYSTEM_DESIGN, IMPLEMENTATION_PLAN, INSTALL)
- Создать новые документы или разделы
- Удалить устаревшую информацию
- Исправить противоречия в документации

**Тогда ИИ должен:**
1. ⚠️ **Явно предложить** пользователю эти изменения в конце ответа
2. 📝 **Кратко обосновать** необходимость изменений
3. 🔗 **Указать конкретный документ** и раздел, который требует изменений
4. ✍️ **Предложить формулировку** для добавления/изменения

**Пример формата предложения:**

```
---
💡 ПРЕДЛОЖЕНИЕ ПО УЛУЧШЕНИЮ ДОКУМЕНТАЦИИ:

📄 Документ: SYSTEM_DESIGN.md
📍 Раздел: Рендер
⚠️ Проблема: Описание PBR-пайплайна разошлось с кодом после рефакторинга RenderPipelinesManager
✅ Предложение: Обновить раздел по фактическому составу Render/PBRRP

Хотите, чтобы я внёс эти изменения?
```

### Структура коммитов

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Типы коммитов**:
- `feat` — новая функциональность
- `fix` — исправление бага
- `docs` — изменение документации
- `style` — форматирование (без изменений логики)
- `refactor` — рефакторинг без изменений функциональности
- `test` — добавление/изменение тестов
- `chore` — изменения в сборке, зависимостях, сабмодулях

**Scope** — имя модуля или подсистемы: `ECS`, `Render`, `Serde`, `UI`,
`CMake`, `Editor`, `Issues` и т.п.

**Пример**:
```
feat(Render): добавить стохастическую прозрачность в PBRRP

- новый проход в PBRRenderPipeline
- шейдеры в Resources/

Closes #123
```

⚠️ В истории встречаются коммиты вида `gui upd` — новые коммиты так
не оформляем.

## 🎭 Роли ИИ

При постановке задачи явно указывай роль, которую должен принять ИИ:

| Роль | Для каких задач | Ключевые компетенции |
|------|-----------------|----------------------|
| **Senior C++ Engine Developer** | Ядро движка: ECS, память, плагины, Serde | C++23, EnTT, архитектура подсистем |
| **Senior Graphics Engineer** | Рендер, шейдеры, оптимизация GPU | OpenGL 4.6/GLES 3.2, PBR, GLSL |
| **Senior Physics/Math Developer** | Физика, трансформации, октодерево | Bullet3, glm, параллельные вычисления |
| **Build Engineer** | CMake, vcpkg, пресеты, кроссплатформенность | CMake, vcpkg-манифесты, триплеты, NDK |
| **Tools Developer** | Редактор, кодогенерация, ImGui | ImGui docking, ANTLR4, MetaInfo |
| **Tech Writer** | Документация, README | Markdown, Doxygen |

Одна задача может требовать нескольких ролей:

```
📝 ЗАПРОС:
"@Senior Graphics Engineer + @Build Engineer:
1. (Graphics) Добавь новый постпроцессинг-проход
2. (Build) Убедись, что шейдеры попадают в install через auto_install"
```

## 🔷 Стандарты кода C++

> 📌 Развёрнутые правила, примеры и грабли — в скилле
> [`cpp-style`](../.claude/skills/cpp-style/SKILL.md). Вызывать его **до**
> того, как открывать код. Первоисточник — [CodingConvention.md](../CodingConvention.md).
> Ниже — только сводка.

### Текущий стек (сверено с CMake на 2026-08-16)

| Что | Значение |
|-----|----------|
| Стандарт | **C++23**, `CMAKE_CXX_STANDARD_REQUIRED ON` |
| Компиляторы | MSVC (`/utf-8`, `/bigobj`, `/EHsc`), Clang/GCC (`-Wall -Wextra`) |
| Ядро | Разделяемая библиотека `SGCore`, экспорт через `sgcore_export.h` |
| Форматтер/линтер | ⚠️ `.clang-format` и `.clang-tidy` в репозитории **отсутствуют** — стиль проверяется только ревью по CodingConvention.md |

### Сводка CodingConvention.md

- Файлы C++ — **UpperCamelCase**; имя файла — по главной структуре в нём.
- Типы и неймспейсы — `UpperCamelCase`; функции и локальные переменные —
  `lowerCamelCase`.
- Члены классов: `m_member`, статические — `s_member`; события/коллбеки —
  без префикса (`onClicked`).
- `constexpr`, `using`, `typedef` — `lower_snake_case`; макросы —
  `UPPER_SNAKE_CASE` или `lower_snake_case`.
- Скобки тела функций/классов/неймспейсов — **на новой строке**.
- Публичные члены — сверху структуры, приватные — внизу; внутри блока:
  вложенные типы → переменные/алиасы → функции.
- Инклуды: библиотеки — `<...>`, свой проект — `"..."`.
- **Запрещено** `using namespace`; смарт-поинтеры при разделяемом владении и
  RAII (следить за циклами); избегать итерации по map'ам.

## 📐 Правила CMake и зависимостей

1. **Новая зависимость — только через `vcpkg.json`** (манифест в корне) с
   указанием минимальной версии. Вендорить в `Externals/` — только если
   пакета нет в vcpkg или нужен форк; причина фиксируется в
   [PROJECT_STRUCTURE.md](./PROJECT_STRUCTURE.md#внешние-зависимости).
2. Появилась новая зависимость или шаг развёртывания — **тем же изменением**
   обновляется [INSTALL.md](./INSTALL.md).
3. Платформенные ветвления — через `SG_TARGET_OS_*` / `SG_TARGET_PLATFORM_PC`
   из `cmake/platform.cmake`, а не через самодельные проверки
   `CMAKE_SYSTEM_NAME`.
4. Пресеты правятся в `cmake/presets/*.json`; новый пресет наследуется от
   `base-presets.json`, чтобы не терять пути через `SUNGEAR_SOURCES_ROOT`.
5. Плагины собираются **тем же пресетом**, что и ядро — правило прошито в
   README и в этом документе, нарушение даёт бинарную несовместимость.
6. Дефайны, закрывающие известные конфликты (`NOGDI`, `NOMINMAX`,
   `WIN32_LEAN_AND_MEAN`, `ANTLR4CPP_STATIC`, `/bigobj`), — **не удалять**
   без проверки причины (см. комментарии в корневом `CMakeLists.txt`).

## 🎨 Ресурсы и шейдеры

- Ресурсы движка (шейдеры, дефолтные ассеты) живут в `/Resources/` и
  загружаются в рантайме — изменения в них не требуют пересборки, но требуют
  установки/копирования (таргет `auto_install`).
- Шейдеры пишутся на GLSL с учётом собственного add-on'а движка; при правке
  сверяться с существующими шейдерами в `Resources/`.
- Не хардкодить пути к ресурсам в C++ — пути идут через `AssetManager`.

## 🧪 Тестирование

**Что есть по факту (2026-08-16)**: один тестовый таргет `SGCoroTest`
(`Tests/Coro/`) — исполняемый файл, проверяющий корутины. GTest заявлен в
`vcpkg.json` (`gtest >= 1.17.0`), но в `Tests/Coro/CMakeLists.txt`
**закомментирован** — фреймворк тестирования фактически не подключён.

Целевое состояние:

| Уровень | Инструмент | Покрытие |
|---------|-----------|----------|
| **Unit** | GTest | Изолируемые подсистемы: Serde, Math, ECS-обвязка, Coro |
| **Функциональные** | Тестовые сцены (`Tests/*`) | Рендер/физика — исполняемые «песочницы» с ручной проверкой |

Правила:

1. Новый тестовый таргет — подкаталог в `Tests/` со своим `CMakeLists.txt`,
   подключённый в `Tests/CMakeLists.txt` (собирается при `SG_BUILD_TESTS`).
2. Логика, не зависящая от GPU/окна (Serde, математика, контейнеры), — под
   unit-тесты; их можно гонять в CI без дисплея.
3. Раскомментирование GTest в существующем таргете — отдельной задачей, а не
   «прицепом».

## 🔄 Git и CI

### Ветки и удалённые репозитории

Основной репозиторий — `Pixelfield-ru/SungearEngine` (GitHub). Работа ведётся
в форках; изменения из upstream подтягиваются мержем `Pixelfield-ru:main`
в свой `main` (так и выглядит история).

| Ветка | Назначение |
|-------|------------|
| `main` | Основная ветка; стабильность фиксируется тегами (`tags/<latest-tag>`) |
| `feature/*`, `bugfix/*` | Рабочие ветки под задачу; вливаются через PR |

### Pull Request

**Чек-лист перед созданием PR**:

- [ ] Код соответствует [CodingConvention.md](../CodingConvention.md)
- [ ] Проект собирается выбранным пресетом (минимум — debug для своей платформы)
- [ ] `SGCoroTest` и затронутые тестовые таргеты собираются и запускаются
- [ ] Обновлена документация (`docs/`, README), если изменение её касается
- [ ] Commit messages следуют конвенции
- [ ] Новые зависимости отражены в `vcpkg.json` и `INSTALL.md`

### Issues

Баги заводятся в трекере `https://github.com/Pixelfield-ru/SungearEngine/issues`
по шаблонам из `.github/` — с версией движка, ОС, архитектурой и минимальным
воспроизведением.

### CI

⚠️ На 2026-08-16 workflow'ов сборки в `.github/` нет — CI-пайплайн не настроен.
Проверка сборки лежит на авторе PR (см. чек-лист выше). Настройка CI — кандидат
в план работ ([IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)).

## 🧠 Скиллы

Перед началом задачи — свериться с [каталогом скиллов](./SKILLS.md#каталог-скиллов)
и **вызвать подходящий до того, как открывать код**. Скилл содержит проверенные
факты и разобранные грабли; догадка о поведении подсистемы стоит дороже одного
вызова.

| Скилл | Брать, когда |
|-------|--------------|
| [`cpp-style`](../.claude/skills/cpp-style/SKILL.md) | любой C++ в `Sources/`, `Plugins/`, `Tests/` |
| [`sgcore-graphics`](../.claude/skills/sgcore-graphics/SKILL.md) | графический слой: `Graphics/`, `Render/`, шейдеры, readback, бэкенды, RHI |

Скилл оказался неполон или неверен — **дополнить его самостоятельно**
(только добавлением, существующие разделы не переписываются) и сказать об этом
одной строкой в ответе. Нужен новый скилл — сначала предложить с обоснованием.
Полный порядок — в [`SKILLS.md`](./SKILLS.md).
