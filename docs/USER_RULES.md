## 🎯 Основные принципы

### 1. Не выдумывай

- **Требование**: если информация неизвестна — прямо говори об этом
- **Запрещено**: придумывать классы, функции, модули, CMake-таргеты, которых
  не существует в движке
- **Действие**: запроси уточнение или предложи проверить исходники

**Пример**:
```
❌ ПЛОХО: "Метод Scene::getOctree() возвращает октодерево сцены"
   (если такого метода нет в коде)

✅ ХОРОШО: "В Scene.h такого метода нет. Октодерево ищи в SGCore —
           предлагаю сначала посмотреть, как оно подключено к сцене"
```

### 2. Не угадывай

- **Требование**: проверяй существующий код перед внесением изменений
- **Запрещено**: предполагать структуру заголовков, сигнатуры, состав модулей
  SGCore без проверки
- **Действие**: читай файлы перед редактированием; движок большой, и названия
  модулей не всегда очевидно отражают содержимое

### 3. Пиши чётко и по делу

- **Требование**: минимум воды, максимум конкретики
- **Структура ответа**:
  1. Краткий ответ/резюме
  2. Детали (если нужны)
  3. Код (если требуется)
  4. Следующие шаги (опционально)

### 4. Проверяй контекст

- **Требование**: перед ответом убедись, что понимаешь контекст задачи
- **Действие**: если контекста недостаточно — задай уточняющие вопросы

## 💬 Правила коммуникации

### Стиль общения

| Аспект | Требование |
|--------|------------|
| **Язык** | Русский (если не указано иное); код, идентификаторы и коммиты — английский |
| **Тон** | Профессиональный, дружелюбный |
| **Длина** | Оптимальная: не слишком кратко, не слишком подробно |
| **Форматирование** | Markdown: заголовки, списки, код-блоки |

### Уточняющие вопросы

Задавай вопросы, если:
- Задача сформулирована неоднозначно
- Недостаточно информации для выполнения
- Есть несколько возможных интерпретаций
- Требуется выбор между альтернативами

**Примеры хороших вопросов**:
```
- "Изменение касается только ПК или Android-сборки тоже?"
- "Новый компонент должен сериализоваться? Тогда нужны Serde-спеки"
- "Правку делать в редакторе v1, v2 или в обоих?"
```

## 💻 Работа с кодом

### Общие требования

| Требование | Описание |
|------------|----------|
| **Конвенция** | [CodingConvention.md](../CodingConvention.md) обязателен; сводка — в скилле [`cpp-style`](../.claude/skills/cpp-style/SKILL.md) |
| **Читаемость** | Код должен быть понятен без комментариев |
| **DRY / KISS** | Избегай дублирования; проще = лучше |
| **RAII** | Владение — через смарт-поинтеры; следить за циклическими ссылками |
| **Кроссплатформенность** | Помнить про Windows/Linux/Android; платформенный код — за макросами `SG_PLATFORM_OS_*` |

### C++-код

```cpp
// ✅ ХОРОШО
struct AudioSource
{
    float m_volume { 1.0f };

    void setVolume(const float& volume) noexcept;

private:
    bool m_isPlaying { };
};
```

```cpp
// ❌ ПЛОХО
struct audio_source {          // имя типа не UpperCamelCase
    float volume;              // член без m_, без инициализации
    void SetVolume(float v);   // функция не lowerCamelCase
};
```

### Проверка изменений

- Изменение обязано **собираться выбранным пресетом** до того, как считается
  готовым.
- На Windows при запуске не забывать про копирование `SGCore.dll`
  (см. [INSTALL.md §6](./INSTALL.md#6-сборка-ядра)).
- Изменения в ядре, затрагивающие ABI/заголовки, требуют пересборки плагинов
  тем же пресетом.

## 🔀 Git: кто что делает

**Коммиты и пуш выполняет пользователь.** ИИ не запускает `git commit`,
`git push`, `git merge` и не создаёт ветки, даже если работа полностью готова
и проверена.

От ИИ по завершении логической единицы работы требуется ровно два артефакта:

1. **Название коммита** — по конвенции из
   [DEV_RULES.md](./DEV_RULES.md#структура-коммитов): `<type>(<scope>): <subject>`.
2. **Краткое summary** — что вошло в коммит, 3–7 пунктов, без пересказа диффа.

**Оба артефакта выдаются одним блоком кода**, готовым к копированию: первая
строка — название, дальше пустая строка и summary списком.

````markdown
```
feat(Serde): поддержка сериализации компонентов навигации

- Serde-спеки для NavMesh-компонентов
- регистрация в StandardSerdeSpecs
- тестовая сцена в Tests
```
````

Если работа не готова к коммиту — так и сказать, а не предлагать название
«на всякий случай».

## 🧰 Инфраструктура — только в INSTALL.md

Всё, что нужно поднять, чтобы репозиторий заработал, описывается **в одном
месте** — [`INSTALL.md`](./INSTALL.md): сабмодули, vcpkg, переменные окружения,
пресеты, сборка, диагностика.

- **Появился новый шаг развёртывания или зависимость — они добавляются в
  `INSTALL.md` тем же изменением, что и код.** Не «потом», не в комментарии
  к коммиту.
- Инструкции не дублируются в README — в README только ссылка.
- Каждый шаг должен быть выполним копированием: реальная команда, а не
  описание словами.
- Проблема, на которую наступили при развёртывании, попадает в
  «Диагностику частых проблем» вместе с причиной и обходным путём.

## 🚫 Запрещённые действия

### Категорически запрещено

1. **Выдумывать API и функции**
   - Не ссылайся на классы и методы движка без проверки их существования

2. **Игнорировать ошибки**
   - Никаких пустых `catch`-блоков; ошибка либо обрабатывается, либо
     пробрасывается с контекстом

3. **Хардкодить значения**
   - Пути к ресурсам — через `AssetManager`; настройки — в конфигурацию,
     магические числа — в constexpr-константы

4. **Ломать кроссплатформенность**
   - Платформенный код без макросов `SG_PLATFORM_OS_*` / CMake-веток
     `SG_TARGET_OS_*` не пишется

5. **Изменять существующий код без необходимости**
   - Минимальные изменения для решения задачи; рефакторинг — отдельной задачей

6. **Редактировать `.gitignore`, `.gitmodules`, `vcpkg.json` без явного запроса**
   - Если нужно что-то добавить/убрать — предложить изменение и дождаться
     подтверждения

### Не рекомендуется

1. **Слишком сложные решения** — избегай over-engineering
2. **Большой scope изменений** — дели большие задачи на мелкие; один PR —
   одна логическая единица
3. **Правки в `Externals/`** — это вендореные чужие проекты; исправления туда
   вносятся осознанно и помечаются

## 🔍 Чек-лист перед завершением задачи

Перед тем как сказать «задача выполнена», проверь:

- [ ] Код соответствует CodingConvention.md
- [ ] Проект собирается выбранным пресетом
- [ ] Затронутые тестовые таргеты собираются и запускаются
- [ ] Нет хардкода путей и платформенных веток без макросов
- [ ] Обработаны edge cases
- [ ] Документация обновлена (если нужно)
- [ ] Выдан блок «название коммита + summary»

## 📞 Эскалация проблем

Если возникла проблема, которую нельзя решить в рамках задачи:

1. **Задокументируй проблему** — опиши суть в начале ответа
2. **Предложи альтернативы** — если есть несколько путей
3. **Запроси решение** — явно спроси, как поступить

**Пример**:
```
⚠️ ПРОБЛЕМА: Изменение требует пересборки skia через vcpkg (~часы).

Варианты решения:
1. Отложить обновление зависимости в отдельную задачу
2. Собрать сейчас и подождать
3. Ограничиться платформами без skia (Android)

Как поступить?
```
